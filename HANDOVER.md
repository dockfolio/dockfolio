## Mental Model

### The KB expansion is validated end-to-end

Session 19 wrote the KB content and shipped the code. Session 20's only job was to prove that four-step path actually works in production: **file on disk → loaded into memory by `loadKBFiles()` → scored against ctx by `scoreKBRelevance()` → injected into the user prompt → consumed by the LLM → visible in output → detected by the citation scanner**. Brief 27 demonstrates ALL six steps for at least one new file (`customer-discovery`) on at least one app (`bannerforge`). That's the proof.

The remaining uncertainty is only about coverage — do all four new files get picked for at least some apps? Dry smoketest from session 19 answered "yes" for customer-discovery on bannerforge, but plg-motions, b2b-outbound, and category-design have NO confirmed production-LLM grounding yet. They're scored-and-retrieved-but-not-yet-cited. Next session's 00:15 UTC cron cycle is the first chance for multiple apps × multiple stages to exercise the new files in parallel. Watch for which topics appear in the `kb_snippets` of briefs 28+.

### The cron-vs-deploy race is a latent hazard

Every deploy that touches files loaded at startup has a window where a cron fire can partially race the rsync. In this case: 20:15 cron fires → starts brief generation → loads the old 12-file KB into memory (because brain-kb.js caches at module load, or at first call) → rsync overwrites `/app/marketing-kb/*` at 20:17 → brief finishes at 20:17 and writes to DB with the OLD kb_snippets. The filesystem reflects the new state but the in-memory KB is stale.

This is mostly self-healing because the container restarts after every rebuild, which flushes the in-memory cache. The exact sequence in session 19's deploy must have been: rebuild container, old container stops, new container starts, cron fires at 20:15 but the new container is still booting… actually, more likely: the 20:15 cron ran in the OLD container (which had the 12-file KB), and the deploy completed afterward at 20:17. Briefs 24-26 all have kb_snippets from the 12-file set, consistent with "ran in old container, was persisted via bind-mounted DB, then the new container started." Not a bug, just a timing artifact.

**Implication for future deploys:** if a cron fires during the rebuild window (a few minutes of downtime + restart), one cron cycle may be lost OR may produce stale results. Not worth fixing — but worth KNOWING so that the first post-deploy cron cycle isn't mistaken for a regression.

### The "customer discovery is NOT useful" section-scoring irony

BannerForge picked the CAVEAT section of customer-discovery instead of the primary content. The scorer picked it because its title contains high keyword density ("customer", "discovery", "useful") — ironically the WARNING-AGAINST section matches better than the TEACHING sections. Session 19's handover predicted this exactly. Real brief 27 confirmed it.

The funny part: the LLM STILL executed the methodology correctly. It saw the caveat section ("Don't do customer discovery when you already have 100+ conversations worth of signal"), understood that bannerforge does NOT have that signal, and pivoted to "therefore you MUST do customer discovery now." The caveat section informed the correct conclusion via negation. This is a good demonstration that the LLM is smart enough to route around imperfect retrieval — retrieval is a hint, not a prescription.

**Don't tune this yet.** The scoring function is producing diverse, useful picks across apps. A fix for the caveat-section bias (down-weight negation sections by ~30%) would be a 1-line change, but without multi-brief production data across 10+ apps, you'd be optimizing on one data point. Wait until you see cron briefs 28-40 and can count how often caveat sections win. If it's < 10%, leave it; if > 30%, tune.

Mitigation: know this and don't panic. Check file timestamps + brief timestamps to diagnose. If sustained over 2+ cron cycles, it's a real bug; if 1 cycle, it's the race.

Fresh clone → fresh deploy → no smoketest binary in container → future validation sessions can't run it. **Highest-priority next-session task.** Fix: add `COPY brain-smoketest.mjs ./` to `dashboard/Dockerfile`.

Until 00:15 UTC cron runs, we don't know if the content is actually reaching the prompt correctly for apps that should trigger these topics. Low risk (session 19's infrastructure was validated thoroughly) but NOT zero.

- **`/home/deploy/marketing/data.db` is the real DB path, NOT `/app/data.db`** — Any future in-container DB queries MUST use the `/home/deploy/marketing/` path. The `/app/*.db` files are 0-byte image placeholders. Getting this wrong wastes 2-3 rounds of debugging (as it did this session).

## What Didn't Work (Traps to Avoid)

- **Assuming `/app/data.db` was the live DB** — It's a 0-byte placeholder. Wasted 3 queries before finding `/home/deploy/marketing/data.db` via `find`. **Next session: always start with `docker inspect dockfolio-dashboard --format '{{range .Mounts}}{{.Source}} -> {{.Destination}}{{println}}{{end}}'` before querying SQLite.**

- **Trying `sqlite3` CLI inside the container** — Not installed. Waste of one command. **Use `node -e` with `better-sqlite3` instead; always.**

- **Trying to curl `/api/brain/kb/usage` from localhost inside the container** — Nginx auth blocks external requests, Express auth blocks internal requests. Same trap session 19 hit. **There is NO way to hit the dashboard API without basic auth from within the container. Go DB-level for telemetry validation.**

- **Initial misreading of the brief table column name** — I guessed `hypothesis` (singular). It's `hypotheses_json`. Use `PRAGMA table_info()` to check the schema before constructing queries with guessed column names. Cost one round-trip.
